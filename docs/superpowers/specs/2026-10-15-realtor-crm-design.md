# CRM-кабінет ріелтора (Польща, Познань): план реалізації на Cloudflare

## Контекст

Агенція нерухомості (власник, який теж веде клієнтів, + до 10 ріелторів) працює в переписках і Excel. Статуси квартир на агрегаторах (Otodom, rynekpierwotny) відстають від сайтів забудовників, тож ріелтори пропонують уже зарезервовані або продані лоти.

Мета — робоче місце, яке:
- двічі на день через **Jina AI** зчитує сайти забудовників і знає статус кожного лоту (wolne / rezerwacja / sprzedane);
- підбирає варіанти під клієнта;
- веде листування, пропозиції, покази, нагадування й угоди в одному місці;
- сповіщає ріелтора про зміни;
- дає власнику повну картину по команді.

**Ваші рішення, вже враховані в плані:**
- джерело статусів — Jina;
- власник бачить усіх клієнтів; при звільненні ріелтор блокується, а клієнти передаються іншому;
- воронка, комісії (суми бачить **тільки власник**), нагадування з історією, імпорт Excel;
- ручне групування дублікатів;
- перевірка розмітки → «кандидат на перегляд»;
- здоров'я джерел бачать власник і **видимий технічний admin** (без доступу до даних клієнтів);
- мова інтерфейсу на вибір;
- без PWA, DB-first на **Cloudflare D1**;
- резерв окремо від продажу;
- усі покращення з першої версії;
- клієнт без логіну;
- стартові забудовники: Ataner, Nickel, Jakon.

План пройшов два незалежні рев'ю (без контексту і проти ваших вимог); знахідки внесено (див. §9). У репо зараз лише чистий Angular 22.

## 1. Бізнес-процес: як є → як буде

| Як є | Як буде |
|---|---|
| Ріелтор шукає на агрегаторах, статус невідомий | База лотів з сайтів забудовників, бейдж «перевірено N год тому», повторна перевірка перед надсиланням |
| Клієнти й домовленості в Excel та чатах | Картка клієнта зі **стрічкою активностей**: нотатки, дзвінки, вхідні та вихідні повідомлення, зміни етапу |
| Власник не бачить, хто що робить | **Командна дошка**: клієнти за етапами × ріелтор, прострочені нагадування, пропозиції за 7 днів, клієнти без активності понад 7 днів |
| Звільнився ріелтор — клієнти пішли з ним | Блокування + майстер передачі; уся історія лишається в системі |
| Комісію у забудовника можна втратити | **Реєстрація клієнта в забудовника** (*zgłoszenie klienta*): дата, підтвердження, термін дії |

**KPI пілоту:**
- кількість пропозицій недоступних лотів → 0;
- час до першої пропозиції після створення клієнта;
- % клієнтів із запланованим наступним кроком;
- % відкритих підбірок.

## 3. Архітектура (Cloudflare)

```
          ┌──── Cloudflare Access (staff) — Worker сам перевіряє JWT Access ────┐
Angular SPA (/app, Workers Static Assets) ──► API Worker (Hono) ──► D1 (--jurisdiction=eu)
Окрема легка сторінка /s/:token (рендерить Worker) ──► /api/public/*  (поза Access)
Telegram webhook /tg/webhook (поза Access, перевірка secret token)
Cron 2×/день ─► Queue "source-run" (1 повідомлення = 1 повний прогін джерела)
   └─► Jina (HTML + X-Target-Selector) → Parser → Validator → staging(run_id)
        └─ прогін повний і валідний → commit diff → listing_events
              ├─► Queue "matching" → proposals / notifications (дайджест)
              └─ missing → повторний прогін через 30–60 хв
Cron */5 хв ─► нагадування та авто-правила
R2 (EU): знімки HTML прогонів · LLM: OpenAI через AI Gateway (логування вимкнено, без PII)
```

**Ключові технічні рішення:**
- **Безпека:**
  - `workers_dev: false`, `preview_urls: false`;
  - middleware перевіряє підпис `Cf-Access-Jwt-Assertion` (`aud`, `iss`) і бере email лише з перевіреного токена; `users.email UNIQUE`;
  - для `users.active` і ролі — запит до БД на кожен виклик;
  - явний список публічних маршрутів: `/s/*`, `/api/public/*`, `/tg/webhook`.
- **Публічна сторінка підбірки** — окремий мінімальний бандл / HTML від Worker під `/s/`, а не весь застосунок:
  - заголовки `X-Robots-Tag: noindex` і `Referrer-Policy: no-referrer`;
  - 128-бітний токен, у БД зберігається лише хеш;
  - ліміт частоти запитів;
  - без URL забудовника, зовнішніх id і контактів відділу продажу (щоб клієнт не обходив агенцію);
  - зі звертання лише ім'я клієнта.
- **DB-first на D1:**
  - SQL-міграції (`wrangler d1 migrations`) з CHECK-обмеженнями;
  - типи генеруються `kysely-codegen`; статуси — спільні TS-константи + тест, що звіряє їх із CHECK у міграціях.
- **D1 без транзакцій:**
  - хелпер `runBatch()` (Kysely compile → `DB.batch()`), заборона `db.transaction()` лінтом;
  - вставка рядок-за-рядком пакетами (ліміт 100 параметрів на запит);
  - передача клієнтів, відкат імпорту й об'єднання дублікатів — ідемпотентні операції з рядком статусу (`operations`), які можна продовжити після збою.
- **Fetch:**
  - лише Jina з `X-Return-Format: html` + `X-Target-Selector` (Jina сама рендерить JS);
  - з одного HTML беруться і дані, і відбиток розмітки;
  - пряме отримання HTML — опція для окремого джерела;
  - Browser Run і circuit breaker прибрано (YAGNI).
- **Парсери:**
  - загальний налаштовуваний парсер (селектори, словник статусів, пагінація в JSON у БД, з версіями та відкатом);
  - для нестандартних сайтів — TS-модуль із golden-тестами.
- **Мова й час:**
  - Transloco (pl / uk) для перемикання мови «на льоту»;
  - адаптивна верстка для телефона (без PWA);
  - зберігання в UTC, показ у Europe/Warsaw.

## 4. Збір даних і статуси

1. **Повний прогін:** одне повідомлення черги = усі сторінки джерела послідовно → staging під `run_id`. Зміни застосовуються **лише якщо всі сторінки успішні й валідні**. Частковий прогін нічого не змінює.
2. **Валідація (ваш п. 9):**
   - кількість лотів збігається з лічильником сайту («Znaleziono N»), якщо він є;
   - пагінацію пройдено до кінця (остання сторінка неповна);
   - обов'язкові поля заповнені, ціни й площі правдоподібні, статуси є у словнику;
   - зникло не більше max(3 лоти, 10%) відносно **останнього доброго** прогону;
   - ріст кількості лише логується.
   - Провал → джерело `needs_review`, дані заморожено, тривога власнику й admin, запускається AI-ремонт (§4a); кандидат чекає на затвердження admin з прев'ю результату.
   - Відбиток розмітки змінився, а перевірки пройшли → лише запис у журнал.
3. **Модель статусу лоту — дві осі:**
   - `availability` — available / reserved / sold / unknown; останнє відоме значення не губиться;
   - `presence` — present / missing / removed;
   - `last_verified_at` — час останнього **успішного** розбору.
   - Правила переходів:
     - зникнення → `missing` і повторний прогін через 30–60 хв;
     - `removed` («ймовірно продано») після 2 повних прогонів поспіль без лоту;
     - повернення лоту застосовується після 2 прогонів.
4. **Перший прогін нового джерела** (або вихід із `needs_review`) не генерує подій, тож немає «шторму» сповіщень.
5. **Повторна перевірка перед відправкою:**
   - кнопка «Підготувати» запускає повторний прогін джерел вибраних лотів;
   - UI опитує статус, після чого вмикаються кнопки надсилання;
   - якщо джерело перевіряли менше 30 хв тому, використовується кешований результат.
6. **Вторинка (у MVP):**
   - ріелтор вставляє посилання → Jina читає оголошення → ріелтор підтверджує поля;
   - щоденна перевірка: «Ogłoszenie nieaktualne» / 404 → `removed`; помилка отримання → `unknown`, а не «знято».
7. **Ручне внесення лоту** для забудовника без парсера.

## 4a. Додавання джерел з інтерфейсу та авто-ремонт парсера

Ідея: нового забудовника додають без розробника, а зламаний парсер система лагодить сама, але **безпечно**.

### Принцип безпеки
- Парсер — це **декларативний конфіг** (селектори, словник статусів, пагінація, мапінг полів), а не код. AI лише пропонує конфіг; виконує його наш детермінований рушій. Тому AI не може «вигадати» статус або ціну в робочих даних.
- Будь-який новий конфіг спершу проходить перевірки на збережених знімках і працює у **тіньовому режимі**; на живі дані він потрапляє лише після успіху всіх перевірок.

### Майстер «Додати джерело» (admin/owner)
1. Вводите URL сторінки зі списком лотів (+ забудовник/інвестиція, тип нерухомості).
2. Кнопка **«Спарсити через Jina»**: Worker забирає HTML, зберігає знімок у R2, показує ліміт токенів.
3. **AI-аналіз** (structured output) знаходить «якорі»: контейнер списку, рядок лоту, номер/id, статус, ціну, ціну за м², площу, поверх, кімнати, URL лоту, пагінацію або лічильник «Znaleziono N». Пропонує словник статусів (напр. «Wolne» → available, «Rezerwacja» → reserved).
4. Рушій **застосовує конфіг до знімка** (без AI) і показує таблицю лотів: підсвічені підозрілі поля, нерозпізнані слова статусу, кількість лотів проти лічильника сайту.
5. **Незалежна перевірка вибірки:** AI читає знімок і перевіряє 5–10 випадкових лотів (статус, ціна) окремо від парсера. Розбіжність → підсвічується.
6. Ви виправляєте мапінг (особливо незнайомі слова статусу — вони **ніколи не мапляться автоматично**) і натискаєте «Зберегти». Створюється `parser_config v1` + **еталонна фікстура** (знімок і очікуваний результат).

### Тест на кожне джерело (автоматично)
- **Контрактний тест на кожному прогоні** — це Validator із §4: лічильник, пагінація, обов'язкові поля, діапазони цін, словник статусів, ліміт зникнень.
- **Регресійний тест на фікстурі:** кожна нова версія конфіга обов'язково відтворює очікуваний результат на збереженому знімку. Після кожного підтвердженого оновлення знімок і результат поповнюють набір фікстур джерела.
- Новий конфіг також тестується на **свіжому знімку** (той, на якому все зламалось).

### Авто-ремонт, коли джерело стало `needs_review`
1. Система збирає пакет: старий конфіг, остання добра фікстура з очікуваним результатом, свіжий HTML (скорочений до контейнера списку), звіт про те, які перевірки впали.
2. AI пропонує **кандидат-конфіг** (максимум 3 спроби, ліміт токенів на джерело).
3. Кандидат проходить усі шлюзи:
   - (а) регресія на старій фікстурі;
   - (б) на свіжому знімку проходить Validator;
   - (в) **безперервність:** ≥90% лотів збігаються за `external_id` з останнім добрим прогоном, ціни незмінних лотів не стрибнули, нових слів статусу немає;
   - (г) незалежна AI-перевірка вибірки;
   - (д) **diff** відносно останнього доброго прогону: скільки лотів змінили статус/ціну, скільки зникло.
4. Рішення:
   - усі шлюзи пройдено, diff «тихий» (зміни в межах порогів) → кандидат стає активною версією, джерело повертається в `ok`, власник/admin отримують повідомлення «виправлено автоматично» з можливістю відкату;
   - будь-який шлюз не пройдено або diff великий → кандидат лишається **на затвердження admin** з прев'ю diff; дані заморожені, статуси не змінюються.
5. На MVP авто-застосування вимкнене: кандидат завжди чекає на затвердження. Перемикач «авто-застосовувати» для джерела вмикається після 3 успішних підтверджених ремонтів поспіль.
6. Версії конфігів зберігаються, відкат в один клік; усі спроби — в `repair_attempts` (причина, витрати, результат шлюзів).

### Ризики і обмеження
- **Сайт змінив зміст, а не верстку** (напр. статус тепер кольором, а не текстом): AI може запропонувати інший якір; шлюз (в) і незалежна перевірка вибірки це ловлять, інакше — затвердження людиною.
- **Багато зламаних джерел одночасно:** черга ремонту послідовна, з денним бюджетом токенів.
- **Сайт став недоступним (403/капча)** — це не поломка парсера: ремонт не запускається, джерело ставиться на паузу з сповіщенням.
- AI не бачить персональних даних клієнтів: у ремонт ідуть лише публічні сторінки забудовників.

## 5. Функції та ролі

**Матриця доступу:**

| Ресурс | owner | realtor | admin | client (токен) |
|---|---|---|---|---|
| Клієнти, активності, пропозиції, покази | усі | свої | — | своя підбірка |
| Лоти, інвестиції | усі | читання + ручне внесення | читання | лише в підбірці |
| Джерела, правила, прогони, здоров'я | так | — | так | — |
| Угоди | усі + суми | свої **без сум комісій** | — | — |
| Комісії, % забудовників | так | — | — | — |
| Користувачі, передача клієнтів | так | — | — | — |
| Командна дошка | так | — | — | — |

Дії admin логуються; admin видимий у списку користувачів.

**Функції MVP:**
- **Клієнти:**
  - ручне створення з перевіркою дубля за телефоном по всій агенції (збіг → конфлікт вирішує власник);
  - `lead_source`, фінансування (готівка / кредит / попереднє погодження), мова, згода RODO (дата + джерело);
  - воронка новобудов (… → *umowa rezerwacyjna* → *umowa deweloperska* → угода) і вторинки (… → *umowa przedwstępna* → *akt notarialny*); етап рухається від угоди (`deals`).
- **Стрічка активностей:**
  - нотатки, дзвінки, вхідні та вихідні повідомлення, зміни етапу;
  - швидкі дії на пропозиції: «клієнт: так / ні / хоче показ» — для відповідей, які приходять у чат.
- **Підбір:**
  - SQL-фільтри + вагова оцінка (ваги в конфіг-таблиці, видно розбивку балів);
  - нові лоти й зміни цін переоцінюються автоматично.
- **Пропозиція — три осі:**
  - доставка: `draft → sent_unconfirmed → sent → opened`;
  - реакція: `none / liked / disliked(причина) / wants_viewing`;
  - результат: `viewing / reserved / rejected`.
  - Таймер «немає реакції 48 год» стартує з першого відкриття або ручного підтвердження відправки.
- **Надсилання:**
  - WhatsApp — `wa.me/<номер>?text=`;
  - Viber і Telegram — «скопіювати текст → відкрити чат» (їхні deep links не підставляють текст надійно);
  - після кліку ріелтор підтверджує «надіслано» → статус `sent` + вихідна активність.
  - Ще на етапі 0 перевіряємо, як ці посилання працюють на телефонах ріелторів.
- **Сторінка підбірки:**
  - 👍 / 👎 з причиною, «хочу показ» з вибором слоту;
  - «відкрито» фіксується JS-подією після завантаження сторінки, ігноруючи ботів превʼю посилань;
  - знятий лот — «недоступно», `missing` — «перевіряється».
- **Покази:**
  - `viewings` і `viewing_slots` (2–3 на пропозицію);
  - адреса й контакт відділу продажу (видно лише ріелтору);
  - ICS-файл.
- **Нагадування з історією:**
  - таблиці `reminders` і `reminder_events`;
  - авто-правила: немає реакції 48 год, показ завтра, протермінована задача, змінився лот у підбірці, закінчується реєстрація клієнта в забудовника.
- **Задачі:** `tasks` (наступний крок по клієнту).
- **Сповіщення:**
  - зміна статусу або ціни запропонованого лоту — одразу;
  - нові збіги — дайджестом раз на прогін на ріелтора;
  - вимкнення сповіщень для окремого клієнта;
  - канали: Telegram-бот команди (ініціали + посилання, без персональних даних) і `notifications` у застосунку.
- **Дублікати:**
  - кожен лот автоматично отримує `property`; пропозиції посилаються на `property_id`;
  - ручне об'єднання й роз'єднання в MVP; статус береться з найдовірчішого джерела, при розбіжності — позначка конфлікту.
- **Звільнення ріелтора:** `active=false` + ідемпотентний майстер передачі (клієнти, задачі, нагадування, покази); історія зберігає автора.
- **Імпорт Excel:**
  - зіставлення колонок, прев'ю;
  - E.164 (номери, які не вдалося розібрати, позначаються, без вгадування);
  - конфлікти з клієнтами інших ріелторів вирішує власник;
  - відкат лише створених і ще не змінених рядків;
  - `import_rows` видаляються через 30 днів.
- **Командна дошка власника:** SQL-представлення з §1.
- **RODO:**
  - D1 і R2 в EU-юрисдикції;
  - AI Gateway без логування;
  - імена, телефони й email вирізаються з тексту перед LLM;
  - анонімізація клієнта по всіх таблицях;
  - Time Travel 30 днів + нічний експорт у R2 з терміном зберігання 30 днів;

## 8. Перевірка
- **Golden-тести парсерів** на знімках Ataner і Nickel (кількість, статуси, ціни, пагінація).
- **Валідація:**
  - впала одна сторінка → нічого не змінюється;
  - зникла половина лотів → `needs_review`;
  - зник 1 лот → `missing` → повторний прогін → `removed` після 2 прогонів;
  - перший прогін нового джерела → 0 подій.
- **Майстер джерел і ремонт (§4a):**
  - додати Ataner через інтерфейс → результат збігається з еталоном;
  - підмінити фікстуру зміненою версткою → джерело `needs_review` → AI-кандидат проходить шлюзи (а–д) і з'являється на затвердження;
  - кандидат, що мапить нове слово статусу або дає >10% зникнень, **не** застосовується автоматично;
  - 403/капча → ремонт не запускається, джерело на паузі;
  - ліміт 3 спроб і бюджет токенів дотримуються.
- **Безпека:** запит до API без валідного Access JWT → 401; підроблений заголовок email → 401; деактивований користувач → 401; `/s/:token` з чужим або відкликаним токеном → 404; ріелтор не бачить чужих клієнтів і сум комісій; admin не бачить клієнтів.
- **D1:** передача клієнтів, перервана посередині, коректно продовжується; батч понад 100 параметрів розбивається.
- **Локально:** `wrangler dev` (локальні D1 і черги), `--test-scheduled`.
- **E2E (етап 1a):** клієнт → прогін → пропозиція → «Підготувати» → надіслати → `/s/:token` → 👍 → сповіщення ріелтору.
- **E2E (етап 1b):** + слот → показ → нагадування «завтра».
- **Пілот:** KPI з §1.

## 10. Оновлення після проходження прототипу (15–16.10.2026)

Ці рішення прийняті під час перегляду клікабельного прототипу (`docs/prototype/rieltor-cabinet.html`) і **мають пріоритет** над попередніми розділами, якщо вони суперечать.

### Клієнти й етапи
- У систему потрапляють лише клієнти, які **вже підписали договір співпраці**. Етапи «Новий», «Кваліфікований», «Покази» прибрано. Покази належать до пропозицій, а не до етапу клієнта.
- Нова воронка: **Підбір → Резервація (umowa rezerwacyjna) → Umowa deweloperska → Передача власності → Завершено** (+ «Втрачено»).
- Відкрите питання: чи лишати «Втрачено», перейменувати на «Співпрацю припинено» чи прибрати зовсім (коментар у прототипі без відповіді).

### Комунальні послуги
- З етапу «Umowa deweloperska» у картці клієнта є чекліст із 5 пунктів: електроенергія (prąd), вода й каналізація, опалення/газ, інтернет, вивіз відходів. Статуси: «Не розпочато» → «Договір подано» → «Підключено». Ріелтор допомагає укласти договори з постачальниками.
- Угоду не можна перевести в «Завершено», поки не підключено всі 5 пунктів.
- У списку клієнтів показується лічильник «комунікації N/5», на дошці власника є список угод з незавершеними комунікаціями, є авто-правило нагадування за 14 днів до передачі.
- Дані: `clients.utils` (5 полів зі статусами) або окрема таблиця `client_utilities(client_id, kind, status, provider, updated_at)`.

### Райони
- Райони міста — **повний довідник** (редагований, а не виведений із наявних інвестицій): таблиця `districts(city, name)`; у `investments` додається `district_id`.
- Критерії клієнта: чекбокси районів вибраного міста («Вибрати всі / Зняти всі»); це **жорсткий фільтр** підбору. Нічого не вибрано = все місто.
- Сторінка «Лоти»: панель районів по містах з кількістю лотів, фільтрує список.
- Сторінка «Підбір» містить **головні критерії** (бюджет, мін. площа, кімнати, райони) для швидкої зміни без виходу зі сторінки, показує, чим відсіяно лоти, і має кнопки розширення пошуку: «Бюджет +10%», «Усі райони міста», «±1 кімната», «Площа −5 м²», «Додати обидва міста».

### Лоти і джерела
- «Лоти» показують **згорнутий список**: рядок на кожного забудовника і окремий рядок «Додані вручну». Список відповідає фільтрам над ним; лоти видно лише після кліку. Є «Розгорнути всі / Згорнути всі».
- Майстер «Додати джерело»: першим кроком обирається **забудовник** (існуючий або новий) і **посилання**, звідки брати квартири; далі Jina → AI-якорі → прев'ю → перевірка вибірки → збереження. Лоти потрапляють під цього забудовника.
- **Ручний лот:** посилання обов'язкове. Перед збереженням Jina перевіряє можливість автомоніторингу (чи видно на сторінці статус і ціну).
  - Знайдено → збереження «з автомоніторингом» (лот перевіряється разом з іншими джерелами; для нього створюється джерело типу `tracked_link`).
  - Не вдалося (403, захист від ботів) → можна змінити посилання або зберегти «з ручним контролем»: позначка «без автоперевірки» і авто-нагадування перевіряти вручну кожні 3 дні.
  - Зберегти без перевірки не можна.

### Мова інтерфейсу
- Додано **російську**: uk / pl / ru. Мова клієнта (повідомлення й сторінка підбірки) задається в картці клієнта окремо.
